# Security — модель угроз и авторизация

**Контекст:** устройство несёт активные радиомодули (CC1101 sub-GHz TX, WiFi inject, NRF24, IR). Управляемость по BLE = управляемость **радио**. Сейчас в прошивке **нет ни pairing/bonding, ни авторизации** (проверено: в `ble_api.cpp`/`BLESerialService.cpp` нет `setSecurityAuth`/auth-callbacks). Значит включённый сегодня BLE-API командуется **любым в радиусе BLE**.

Решение для v1 (зафиксировано): **токен в `HELLO`**. Полноценный bonding — Phase 6.

---

## Модель угроз

| Актор | Возможность сейчас | После v1 (токен) | После Phase 6 (bonding) |
|---|---|---|---|
| Случайный BLE-сканер | видит `Bruc`, может слать команды | команды отвергаются без токена | требуется спаренность + токен |
| Атакующий в радиусе, знает протокол | полный контроль радио | нужен секрет (не передаётся в эфир как plaintext при правильной реализации) | + шифрование канала, защита от подмены |
| Пассивный сниффер эфира | читает весь трафik (канал не шифрован) | читает трафик, но не команды без валидной сессии | канал зашифрован (bonding/SC) |
| MITM | возможен | возможен (Just Works не защищает от MITM) | частично (numeric comparison при наличии IO) |

> Вывод: токен закрывает «любой может командовать», но **не** шифрует канал. Полная конфиденциальность/anti-MITM — за bonding (Phase 6), и то Just Works от MITM не спасает.

---

## v1 — токен в `HELLO`

- Поле конфига `companionToken` (`BruceConfig`, см. [`firmware.md`](firmware.md#5-конфиг-флаг-и-токен)). Генерируется на устройстве (показывается в меню/QR, как `webUI`-креды) и вводится в хост-приложении один раз.
- Рукопожатие: `→ REQ 1 HELLO proto=1 token=<secret>`. Несовпадение → `← ERR 1 7 AUTH`, framed-режим **не включается**, прочие команды не принимаются.
- **Рекомендация по реализации, чтобы не светить токен в эфире открытым текстом:**
  - challenge-response: `HELLO` без токена → устройство шлёт `nonce` → хост отвечает `HMAC(token, nonce)`. Так секрет не идёт по незашифрованному BLE plaintext'ом.
  - (минимальный вариант v1 — plaintext-токен; приемлемо только в доверенной среде, отметить в UI).
- Тайм-аут/лимит попыток: после N неверных `HELLO` — пауза/разрыв (анти-brute по BLE).
- При `companionEnabled=false` — framed-путь вообще не активен (поведение прошивки = текущее).

---

## Phase 6 — bonding + hardening

- NimBLE `setSecurityAuth(bond, mitm, sc)`: bonding + LE Secure Connections → шифрование канала, хранение ключей.
- Just Works (без IO для numeric comparison на устройстве можно использовать дисплей для passkey — у T-Embed экран есть, значит **passkey/numeric comparison реально**, что закрывает MITM лучше Just Works).
- Per-session токен/ротация поверх зашифрованного канала.
- Привязать «разрешённые» команды к уровню авторизации (например, TX/jam — только после bonding).

---

## Операционные замечания

- `jam_sweep`, `tx*`, `responder`, `sniffer` — потенциально регулируемые/незаконные в эфире действия. UI хоста должен явно подтверждать такие команды (а не выполнять по случайному клику), независимо от авторизации.
- Логирование: вести аудит-лог отправленных команд на хосте (что/когда/каким транспортом) — полезно и для отладки, и для подотчётности.
- `factory_reset`, `poweroff`, `file put` в системные пути — требуют подтверждения в UI.
