# Companion Wire Protocol v1

Кадровый протокол поверх существующего строкового командного интерфейса Bruce. Цель: минимальная сложность кодирования/декодирования в C++ (прошивка) и в Rust/Python (хост), один кадр на один BLE-write, и при этом человекочитаемость при отладке через USB-терминал.

- **Транспорт-агностичен**: те же кадры идут и по BLE (характеристика `d555ed97-…`), и по USB-CDC.
- **Обратная совместимость**: если хост не прислал `HELLO`, прошивка работает в legacy-режиме (текущий человеческий CLI с `# `-промптом). Обычный BLE-UART терминал продолжит работать.
- **Версионируется**: `proto=N` в рукопожатии.

---

## 1. Кадр (frame)

Строково-ориентированный, завершается `\n`. **Один кадр = один BLE-write.**

```
<TYPE> <ID> <PAYLOAD...>\n
```

| Поле | Описание |
|---|---|
| `TYPE` | тип кадра: `REQ`, `RSP`, `END`, `ERR`, `EVT`, `ACK` (см. ниже) |
| `ID` | uint, монотонно растущий, назначается хостом для `REQ`; эхо-возврат в `RSP`/`END`/`ERR`; `EVT` использует ID породившего `REQ` или `0` для несолицитированных событий |
| `PAYLOAD` | для `REQ` — обычная Bruce-команда дословно (например `wifi scan`); для `RSP`/`EVT` — одна строка вывода; для `END` — код статуса; для `ERR` — `<code> <message>` |

Кодировка по умолчанию — **ASCII/UTF-8, line-safe**. Бинарные данные (файлы) передаются **base64** внутри `EVT chunk`, чтобы весь протокол оставался строковым (и совместимым с `readStringUntil('\n')` в прошивке).

> Внутри `PAYLOAD` символ `\n` запрещён (он — разделитель кадров). Многострочный вывод команды разбивается на несколько `RSP`-кадров.

### Типы кадров

| TYPE | Направление | Смысл |
|---|---|---|
| `REQ` | host → device | запрос: команда на выполнение |
| `RSP` | device → host | одна строка вывода в ответ на `REQ <ID>` |
| `END` | device → host | конец ответа на `REQ <ID>`, несёт код результата |
| `ERR` | device → host | ошибка обработки `REQ <ID>` (вместо/до `END`) |
| `EVT` | device → host | асинхронное событие (прогресс, захваченный пакет, чанк файла) |
| `ACK` | host → device | поток-контроль/подтверждение (для chunked-передачи и будущего credit-flow) |

**Ключевое преимущество над текущим протоколом:** надёжный маркер конца — `END <ID> <code>`. Сейчас единственный признак конца — печать `# ` (`serialcmds.cpp:52`), что ненадёжно для машинного парсинга.

## 2. Рукопожатие и авторизация (`HELLO`)

Первый кадр сессии. Включает framed-режим и проводит авторизацию по общему секрету (см. [`security.md`](security.md)).

```
→ REQ 1 HELLO proto=1 token=<secret>
← RSP 1 fw=Treecataje/1.14 proto=1 board=T_EMBED_CC1101 mtu=247 name=Bruc
← RSP 1 caps=wifi,rf,ir,nrf,gpio,crypto,storage,status,gps,util,settings,power,sound,screen,badusb,js
← END 1 0
```

> `HELLO` всегда отвечает ровно двумя `RSP`-кадрами — (1) `fw/proto/board/mtu/name`, (2) `caps=…` — и затем `END <id> 0`. Хост парсит по префиксу поля, порядок строк фиксирован.

- `proto=` — версия протокола, на которой говорит хост; прошивка отвечает своей.
- `token=` — общий секрет; при несовпадении: `← ERR 1 7 AUTH` и framed-режим **не включается** (никакие другие команды не принимаются).
- `caps=` — список включённых групп команд, выводится из тех же `#ifdef`, что гейтят регистрацию в `cli.cpp` (`USB_as_HID`→badusb, `LITE_VERSION`→js, `HAS_SCREEN`→screen, `HAS_NS4168_SPKR`/`BUZZ_PIN`→sound). Хост предлагает в UI только то, что реально есть на устройстве.
- `mtu=` — согласованный ATT MTU (для расчёта размера чанков при передаче файлов).

После успешного `HELLO` сессия — framed; до него прошивка остаётся в legacy-режиме.

## 3. Коды результата/ошибки

Малый перечень (в `END <ID> <code>` и `ERR <ID> <code> <msg>`):

| код | имя | смысл |
|---|---|---|
| 0 | `OK` | успех |
| 1 | `PARSE` | команда не распознана/неверные аргументы |
| 2 | `BUSY` | нужный ресурс занят модальной фичей устройства (см. арбитраж в [`firmware.md`](firmware.md)) |
| 3 | `UNSUPPORTED` | команда не скомпилирована в этой сборке (нет в `caps`) |
| 4 | `IO` | ошибка ввода-вывода (SD/радио/файл) |
| 5 | `TIMEOUT` | таймаут выполнения |
| 6 | `BADFRAME` | некорректный кадр/нарушение протокола |
| 7 | `AUTH` | не пройдена авторизация (`HELLO`) |

## 4. Примеры обмена

### 4.1. Дискретная команда (re-use существующего вывода)

В v1 «дешёвый путь»: не переформатируем текстовый вывод существующих команд — каждую строку вывода помечаем `RSP <id>`, в конце `END <id> <code>`.

```
→ REQ 7 wifi scan
← RSP 7 [WiFi] scanning...
← RSP 7 1) HomeNet  -52dBm ch6  WPA2
← RSP 7 2) Cafe     -71dBm ch11 OPEN
← END 7 0
```

### 4.2. Структурированный скан (опциональная доработка — новый `companion`-глагол)

Позднее можно добавить companion-команду, выдающую разобранные поля как события:

```
→ REQ 7 companion wifi scan
← EVT 7 ap ssid="HomeNet" bssid=aa:bb:cc:dd:ee:ff rssi=-52 ch=6 enc=WPA2
← EVT 7 ap ssid="Cafe"    bssid=11:22:33:44:55:66 rssi=-71 ch=11 enc=OPEN
← END 7 0
```

### 4.2.1. Статус занятости радио (`companion busy`)

```
→ REQ 5 companion busy
← RSP 5 owner=none              # none | ui | companion
← END 5 0
```
Если радио занято модальной фичей UI, любая radio-команда вернёт `← ERR <id> 2 BUSY` (см. арбитраж в [`firmware.md`](firmware.md#4-арбитраж-ресурсов-busy)).

### 4.3. Старт/стоп потоковой задачи

```
→ REQ 12 companion stream start beacon
← RSP 12 streaming=beacon id=12
← EVT 12 pkt t=1234 bssid=aa:bb:.. rssi=-60
← EVT 12 pkt t=1240 bssid=cc:dd:.. rssi=-58
        ...
→ REQ 13 companion stream stop 12
← RSP 13 stopped=12
← END 13 0
← END 12 0
```

`companion stream …` — **новый** глагол (см. [`command-catalog.md`](command-catalog.md)) с явными start/stop и под busy-флагом. Под капотом переиспользует существующие сканеры/снифферы прошивки.

### 4.4. Передача файла захвата (device → host)

Чанкованная, base64, с проверкой целостности. Размер чанка считается от согласованного `mtu` (с запасом на префикс кадра и base64-инфляцию ×4/3).

```
→ REQ 20 companion file get /sd/captures/x.sub
← RSP 20 size=4096 chunks=16 chunk_size=256 sha256=<hex>
← EVT 20 chunk 0 <base64...>
← EVT 20 chunk 1 <base64...>
        ...
← EVT 20 chunk 15 <base64...>
← END 20 0
```

Хост собирает файл и сверяет sha256. При потере чанка хост может запросить переотправку: `→ REQ 21 companion file get /sd/captures/x.sub range=7-7`.

> Base64 — стандартный RFC 4648 с паддингом, **без** внутренних переводов строк (один чанк = один `EVT`-кадр одной строкой). Формат: `EVT <id> chunk <n> <base64>`.

**Host → device (загрузка):** зеркально, переиспользует существующий механизм записи файла с EOF-сентинелом (`storage_commands.cpp` / `helpers.cpp`):

```
→ REQ 30 companion file put /sd/uploads/payload.sub size=2048 sha256=<hex>
← RSP 30 ready chunk_size=256
→ EVT 30 chunk 0 <base64...>
← ACK 30 0          # подтверждение чанка (поток-контроль)
→ EVT 30 chunk 1 <base64...>
← ACK 30 1
        ...
← END 30 0          # после сверки sha256
```

## 5. Поток-контроль и MTU

- v1: для исходящего трафика устройства действует встроенный потолок `vTaskDelay(10ms)` на `notify` (см. [`firmware.md`](firmware.md#8-известные-узкие-места)). Хост просто читает нотификации; явный credit-flow для device→host в v1 не нужен.
- Для host→device при `file put` — простой stop-and-wait: устройство шлёт `ACK <id> <chunk>` после записи каждого чанка (защищает медленную запись на SD).
- `mtu` берётся из `onMTUChange` (`ble_api.cpp:16,40`). Хост рассчитывает `chunk_size = floor((mtu - 3 - len("EVT <id> chunk <n> ")) * 3/4)`.
- **Phase 6** (опц.): заменить blanket-delay на credit-схему (`ACK`-окно) и поднять MTU/DLE для роста пропускной способности.

## 6. Версионирование и совместимость

- `proto=1` — этот документ. Несовместимые изменения → `proto=2`, прошивка может поддерживать несколько версий и выбирать по `HELLO`.
- Неизвестный `TYPE` или мусорный кадр → `ERR <id|0> 6 BADFRAME`, сессия не рвётся.
- Неизвестная команда → `ERR <id> 1 PARSE` (через существующий `cliErrorCallback`, обёрнутый в кадр).
- Без `HELLO` → legacy human-CLI (полная обратная совместимость с любым BLE-UART/serial-терминалом).

## 7. Резюме реализации (почему дёшево)

- **Входящий путь:** разобрать первые два токена кадра (`TYPE`, `ID`), остаток отдать в `SerialCli.parse()` (существующий диспетчер). Никаких изменений в 80+ командах.
- **Исходящий путь:** `FramingSerialDevice` (декоратор поверх реального `SerialDevice`) префиксует каждую строку `RSP <id> ` и в конце `parse()` дописывает `END <id> <code>`. Тела команд не трогаем.
- **`EVT`** — тот же писатель, что и вне запроса, но `TYPE=EVT`.
- **Авторизация** — проверка одного поля в `HELLO`.

Детали привязки к коду — в [`firmware.md`](firmware.md).
