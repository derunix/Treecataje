# Companion Device Mode — спецификация и план

Режим **устройства-компаньона** для прошивки Bruce-форк (`Treecataje`) на **LilyGO T-Embed CC1101 Plus** (ESP32-S3) + Linux-приложение на хосте (**uConsole** и x86) в двух фронтах: интерактивный **TUI** и **GUI**.

> **Главный принцип:** компаньон **расширяет**, а не заменяет. Автономный (standalone) функционал устройства не должен пострадать. Компаньон — это дополнительный канал управления и выгрузки данных поверх уже существующей машинерии прошивки.

## Идея в одном экране

Устройство (T-Embed CC1101) — это автономный «радио-мультитул» на ESP32-S3 с CC1101 (sub-GHz), WiFi (monitor/inject), NRF24, IR, экраном и SD. У него уже есть:

- **диспетчер команд** `SerialCli` (SimpleCLI) с 80+ командами (WiFi, RF, IR, NRF, GPIO, crypto, storage, GPS, settings, …) — `src/core/serial_commands/`;
- **BLE-«последовательный порт»** `BLESerialService` поверх NimBLE — `src/modules/ble_api/`;
- **отдельный FreeRTOS-таск** обработки команд, работающий **параллельно** с UI — `src/core/serialcmds.cpp`, запуск в `src/main.cpp:509`.

Компаньон-режим = тонкая надстройка, которая:

1. оборачивает существующий командный ввод/вывод в **кадровый протокол** (request id, маркер конца ответа, коды ошибок, асинхронные события) — чтобы хост-программа могла надёжно парсить ответы и подписываться на потоковые данные;
2. ходит по пути **без `backToMenu()`**, поэтому не выкидывает пользователя из текущего экрана — автономность цела;
3. требует **токен** в рукопожатии (устройство с радиомодулями не должно слушаться любого в радиусе BLE);
4. всё это — за конфиг-флагом, по умолчанию **выключено**: при выключенном флаге поведение прошивки идентично текущему.

На стороне хоста — общее ядро (транспорт BLE/USB + кодек протокола + сессия + шина событий) и два тонких UI поверх него.

## Host-compute augmentation (расширение вычислительной мощностью хоста)

> Это — ответ на требование «полный функционал устройства, расширенный доступными вычислительными мощностями».

Разделение ролей:

```
┌─────────────────────────────┐        BLE / USB        ┌──────────────────────────────┐
│  T-Embed CC1101 (ESP32-S3)  │  ◄───────────────────►  │  Хост: uConsole / x86 (Linux) │
│  «RF / периферийный фронт»  │   кадровый протокол     │  «вычислительный бэкенд»      │
├─────────────────────────────┤                         ├──────────────────────────────┤
│ • радио I/O (CC1101/NRF/WiFi)│                         │ • тяжёлый разбор/декодирование │
│ • захват в файл на SD       │   выгрузка захватов     │ • brute/dictionary, аналитика  │
│ • базовые сканы/события     │   ──────────────►       │ • визуализация, БД захватов    │
│ • маломощный CPU/RAM        │                         │ • корреляция, экспорт, отчёты  │
└─────────────────────────────┘                         └──────────────────────────────┘
```

Принцип: **устройство добывает сигнал, хост его осмысляет.** Что именно выносится на хост (детали — в [`host.md`](host.md#host-compute-augmentation)):

- **WiFi:** устройство ловит хендшейки/PMKID → выгрузка `.pcap`/`.hccapx` → хост гоняет hashcat/aircrack по словарям; разбор и визуализация эфира.
- **Sub-GHz (CC1101):** устройство пишет сырой/`.sub` захват → хост декодирует протоколы, ищет rolling-code паттерны, строит спектр/таймлайны, готовит реплей.
- **NRF24:** устройство сниффит → хост разбирает payload'ы, профилирует устройства.
- **IR/RFID/NFC:** устройство снимает дамп → хост нормализует, ведёт библиотеку, конвертирует форматы.
- **Общее:** единая локальная БД захватов на хосте, теги/гео-привязка (через GPS устройства), экспорт/отчёты, скриптинг.

Это полностью укладывается в протокол: «команда → запуск на устройстве → события прогресса → выгрузка файла-результата → обработка на хосте». Никаких изменений философии — только новые `companion`-глаголы и host-модули.

## Жёсткие ограничения (проверено по исходникам)

1. **`serialDevice` — один глобальный указатель** → BLE и USB-CDC **взаимоисключающи**, активен один транспорт за сессию (`src/modules/ble_api/ble_api.cpp:32,53`). Для хоста удобно: один транспорт на подключение.
2. **`backToMenu()` после каждой команды** (`src/core/serialcmds.cpp:53`) ломает текущий экран UI → именно это обходим в компаньон-пути.
3. **BLE-«serial» пакетный, не потоковый**: один BLE-write = одно логическое сообщение (`BLESerialService::available()`/`readStringUntil()` читают значение характеристики целиком) → **один кадр на один write**.
4. **Пропускная способность ограничена самой прошивкой**: `vTaskDelay(10ms)` после каждого `notify()` (`BLESerialService.cpp`) → ~100 пакетов/с. Practical ceiling ~2 КБ/с при MTU 23, ~24 КБ/с при MTU ~247. Вывод: дискретные команды/события/файлы — ок по BLE; высокочастотный live (спектр, сырой поток) — только USB или «захват в файл → выгрузка».
5. **ESP32-S3 = только BLE**, нет Bluetooth Classic / SPP. «Связь по BT» = BLE (GATT central на хосте).

Подробные последствия и обходы — в [`firmware.md`](firmware.md) и [`protocol.md`](protocol.md).
